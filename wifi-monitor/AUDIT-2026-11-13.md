## B. Architecture

```text
Ordinary Wi-Fi
  Android Wi-Fi service / HAL / supplicant → nl80211 → cfg80211 → gen4m AIS
  Linux network stack ↔ wlan0 Ethernet netdev ↔ gen4m queues ↔ CONNAC2 firmware

Passive setup
  Explicit root helper → iw and ip → nl80211 and rtnetlink
    → cfg80211 → gen4m interface role and channel callback
    → kalIoctl → wlanoidSetMonitor → CMD_ID_SET_MONITOR → firmware

Passive capture
  CONNAC2 → AXI PDMA RX ring → gen4m CONNAC2 descriptor parser
    → radiotap skb → primary monitor netdev → Linux packet capture

Passive TX
  Radiotap netdev → wlanHardStartXmit → skb consumed and dropped
```

Android remains the owner of normal Wi-Fi. The helper requires a preloaded test
driver and a down, managed `wlan0` while Android Wi-Fi is off. This driver
converts an existing netdev and changes an adapter-wide RX mode. It does not
create an independent concurrent capture radio. On the inspected 6.1 cfg80211
tree, channel setup requires at least one running monitor and no running
non-monitor interfaces on its wiphy. The vendor command is fire-and-forget.
The callback can report host-side failure, while actual tune and receive
behavior need an independent capture observation. [Linux cfg80211 documentation](https://kernel.org/doc/html/next/driver-api/80211/cfg80211.html)

The selected wiphy management subtype table has no monitor TX entry, so
cfg80211 rejects monitor management TX before calling the driver. Firmware
behavior and unintended traffic during role changes still need to be
checked with an independent receiver.

The historical injection patch is outside the supported build. The audit
identified unresolved frame validation, TX resource isolation, managed-role
restoration and firmware behavior concerns in that path. No injection build,
fixture, firmware change or over-the-air test was performed.

The private monitor command used integer conversions with byte- and short-sized destinations. Enabling radiotap exposed a kernel memory-safety defect through the private command dispatcher. | Removed the command entry, implementation and declarations. nl80211 supplies the supported configuration path. |
| High / conditional on segmented traffic and RX ring state | `Kbuild.main:1190–1193`, `os/linux/hif/common/kal_pdma.c:2373–2494`. Recovery ignored removal/reload failures and enabled Wi-Fi irrespective of the initial state. This could disrupt normal Wi-Fi even without using monitor mode. | Retired the runtime loader and its boot hook. The helper carries no kernel payload. ## F. Performance and safety assessment

The helper has no boot service, background process or periodic check. Managed
Wi-Fi with the passive driver loaded reserves 128 bytes of radiotap headroom
on the relevant RX allocation paths and adds mode checks. These compile-time
changes and the matched wireless stack can affect ordinary Wi-Fi through allocation,
driver/firmware interaction, power management or cfg80211 behavior. Throughput,
latency, CPU, memory, battery and thermal effects were not measured.

For a controlled comparison, use the same handset, stock firmware, build
settings, AP and placement. Hold the channel and signal conditions fixed and
alternate stock and candidate runs. Record an idle and load baseline in each
direction. Use five paired 60-second throughput runs per band, five latency
runs with loss and p95 jitter, and at least two matched 30-minute screen-off
intervals for idle current, residency, CPU wakeups and temperature. Log RSSI,
negotiated rate, channel width and retransmissions. Treat a repeatable decline
beyond stock run-to-run noise as a regression. Initial thresholds for review
are 5% median throughput, 10% p95 latency/jitter, 0.5 percentage points of loss,
5% idle current and 2°C sustained temperature increase at comparable load.
Any disconnect loop, unrecovered interface, kernel/firmware reset, increasing
buffer use across cycles or new thermal throttling is a failure regardless of
aggregate results.

## G. Remaining hardware and integration gates

1. Qualify a dedicated test ROM for the exact handset and current stock
   firmware. Preserve the known-good complete boot and module set and a
   verified recovery path. Check the device variant, loaded module identity,
   load order, enforcing SELinux, firmware version and command logs. A CRC
   match alone cannot prove a load or runtime compatibility.
2. Boot and exercise ordinary Wi-Fi first. Check association and reconnection
   on both bands, scan, hotspot, roaming, suspend/resume and Bluetooth
   coexistence. Compare results with stock before enabling capture.
3. Verify that turning Android Wi-Fi and hotspot off leaves a down, managed
   `wlan0` on a ready driver. The framework can remove the interface or power
   down WLAN when disabled. The helper stops safely in that case and this
   integration still needs a viable radio lifecycle for that ROM.
4. In a controlled RF environment, capture beacons from a known AP on channels
   6 and 36. Compare radiotap frequency, frame type, lengths, FCS indication
   and field decoding with an independent receiver. Keep the first capture to
   single-descriptor RX. Repeat at least 20 arm/disarm cycles, check for queue
   and memory growth, and repeat across screen-off/wake. Channel readback,
   RX metadata across frame types, teardown after suspend, and recovery from
   a missing firmware response are still hardware-dependent.
5. Abort on a firmware assertion, Oops, persistent packet starvation,
   monitor-to-managed failure, connectivity regression or unexpected radio
   behavior. If disarm fails, leave the Android Wi-Fi framework disabled
   while collecting logs and restore the approved stock test image/module set
   through the prepared recovery procedure. Removing the helper only removes
   the UI and commands. Keep calibration, regulatory data, DTBO and firmware
   partitions outside the test change.
